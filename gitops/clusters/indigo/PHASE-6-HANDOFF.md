# Indigo Gateway handoff

## Architecture

Private DNS resolves `argocd.indigo.home.arpa` to `10.10.60.100`.
Caddy on `srv-lx-gateway` proxies with verified origin TLS to the MetalLB VIP
`10.10.80.200`. Envoy Gateway owns the shared Gateway and its two proxy replicas;
the Argo HTTPRoute selects `argocd-server`. Vault issues the certificates.
Cilium remains responsible for pod networking, Service networking, L7 policy
and observability. Its Gateway API controller is retired.

OPNsense holds the DMZ interface rule from `10.10.60.100/32` to `INDIGO net`
using `DMZ_Ports`, and the private DNS override. These are router-managed state,
not currently generated by either repository. The firewall rule is broader than
the single Gateway VIP; review that scope during Phase 8 hardening.

## Repeatable reconciliation

Application YAML is generated from `gitops/templates/applications`.
Indigo's Application Kustomization opts into the reusable
`gitops/components/gitops-policy/steady-state` component. New clusters can opt in
after controlled adoption; hub-a retains its existing policy.

- All Indigo Applications automatically sync and self-heal.
- Controller/API Applications retain `prune: false`: Cilium, Envoy Gateway,
  External Secrets, Gateway API, CSR approver, MetalLB and Metrics Server.
  Removal requires reviewing the exact resources and issuing a pruning sync.
- Configuration Applications automatically prune with `PruneLast=true`.
- Foundation namespaces retain their existing explicit deletion confirmations.
- Empty automatic pruning remains disabled by default.

Fast local verification (no Nix build):

```sh
node packages/gitops/src/bin/generate.ts --check
node packages/gitops/src/bin/check.ts
node --test tests/indigo-gitops.test.ts tests/gitops-cli.test.ts tests/gitops-generate.test.ts
```

Argo comparison drift was corrected at source: explicit HTTPRoute backend weight,
ExternalSecret API defaults, and removal of an empty directory source option.

## Controlled failover evidence — 2026-09-04

The proxy on worker-03 (then the MetalLB announcer) was evicted through the
policy/v1 Eviction API with its disruption budget intact. The surviving proxy
was on worker-01. Kubernetes restored two ready replicas, placing the replacement
on worker-02; MetalLB's announcement also settled on worker-02.

One hundred HTTPS requests through Caddy validated certificates on the normal
private path. Ninety-nine returned HTTP 200. One returned HTTP 502 during the
transition; Caddy logged an upstream connection reset. The next sample succeeded
and service recovered without intervention. Existing Argo event streams also
reconnected. This proves recovery from a voluntary single-proxy disruption, not
zero dropped requests or survival of physical-host failure.

Phase 8 should assess bounded retries for safe requests at the central proxy
and graceful connection draining. All six Kubernetes VMs currently share one
physical host, and central Caddy remains a separate availability dependency.

## Why there are 14 Argo Applications

The count represents ownership and reconciliation boundaries, not 14 Argo
servers: root, Argo configuration/access, foundation, Cilium, Gateway API,
Envoy controller, Gateway configuration, External Secrets controller/config,
MetalLB controller/config, CSR approver and Metrics Server. Keeping controllers
separate from configuration allows independent upgrades, restricted projects,
and different pruning policies. Argo access files remain under the argocd
component even though they have a separate Application for their API dependencies.
